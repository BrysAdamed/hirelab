# Glossary

Use these terms in code, API, UI and tickets. When you introduce a new domain term, add it here.

| Term | Meaning |
|---|---|
| **Job position** | An opening the team is hiring for: a title and the Markdown sections description, requirements (required), nice-to-haves and interviewer notes. Its state is `Open` or `Closed`; a closed position is read-only. The manager creates, edits and deletes positions (delete only while open and without candidates); interviewers read them. In code: `JobPosition`. |
| **Version** | The number an editable aggregate is read with (PostgreSQL `xmin`). An edit sends it back; if someone else saved in between, the edit is refused with "changed by someone else, reload". |
| **Candidate** | A person applying to exactly one job position. The same person applying again is a new candidate. Has a full name, an optional email and phone, up to 3 profile links and a number. The manager and interviewers of the team add and edit candidates while the position is open. Their personal data lives only in Positions; other modules hold the candidate id (ADR 0023). In code: `Candidate`. |
| **Candidate number** | A candidate's place in their position's sequence (1, 2, 3 …), given when they are added and never changed or reused. |
| **Candidate #N** | How an anonymised candidate is shown, N being their candidate number. Otherwise a candidate is shown by full name. In code: `Candidate.DisplayName`. |
| **Attachment** | A file on a candidate's profile. The CV is an attachment. PDF, DOCX, TXT, MD, PNG or JPG, at most 10 MB, at most 10 per candidate. The manager and interviewers of the team upload and delete them while the position is open and download them any time; anonymisation deletes them (ADR 0005, ADR 0024). In code: `Attachment`. |
| **Anonymisation** | Removing a candidate's personal data: contact details are cleared, attachments are deleted and the candidate is shown as "Candidate #N" everywhere. Who did it and when is recorded (`AnonymisedBy`/`AnonymisedAt`). Closing a job position anonymises all its candidates. Notes, scores and task results stay. It is irreversible. |
| **Anonymise candidate** | Anonymising a single candidate while their position stays open. Manager only, refused while the candidate has an unfinished session (ADR 0026). |
| **Close position** | The manager ending hiring for a job position: it becomes `Closed` and read-only, who closed it and when is recorded (`ClosedBy`/`ClosedAt`) and all its candidates are anonymised. Refused while any of its candidates has an unfinished session. Irreversible (ADR 0026). |
| **Unfinished session** | An interview session that isn't `Finished` yet (`Planned` or `Live`). It blocks closing the position and anonymising the candidate. In code: `IUnfinishedSessionsQuery`. |
| **Task** | One interview exercise, authored in the app. It has an owning team, a visibility, versions, a task type, title, summary, tags, level, estimated minutes, content, reference answer, interviewer notes and rubric. Its UI comes from its task type. In code: `InterviewTask` (`Task` clashes with .NET's), table `tasks` (ADR 0029). |
| **Task version** | One revision of a task (`v1`, `v2` …). Published versions are immutable; a change means a new version. Its state is `Draft` or `Published`. In code: `TaskVersion`. |
| **Draft** | The one unpublished version a task may have. Editable by the team; can be previewed, but queued only in Development. |
| **Active version** | The task version the task bank offers. By default the newest published one; the manager can switch it. A draft is never active, and a system task always uses its newest version. In code: `InterviewTask.ActiveVersion`, `IActiveTaskVersionQuery`. |
| **Visibility** | Whether a task is seen by its owning team only (`Team`) or by every team (`Global`). Only the owning team edits it. |
| **System task** | A showcase task imported from a seed package in the repo. Global, owned by no team, read-only, identified by its slug. |
| **Slug** | A system task's external key: its seed package folder name, kebab-case and unique. Seed import matches tasks by slug and version number. |
| **Archived task** | A task taken out of the task bank for good, because it was queued and so can't be deleted. Sessions keep their snapshots of it. Who archived it and when is recorded. |
| **Task version details** | What an author writes for a task version: title, summary, level, estimated minutes, tags, reference answer, interviewer notes, rubric and content. They become a version only after the one task version validation (generic rules, then the task type's), which seed import and the editor share. In code: `TaskVersionDetails`, `TaskVersionValidator`, `ValidatedTaskVersion`. |
| **Content hash** | The SHA-256 of a task version's validated details and content, ignoring JSON formatting. Seed import compares it to detect a changed seed version; the tasks lock hashes the package files instead (ADR 0030). |
| **Task version snapshot** | What a session task copies from the version it pins: content, reference answer, interviewer notes and rubric, with the version's id and title. In code: `TaskVersionSnapshot`. |
| **Seed package** | A task version stored as a folder `src/Tasks/<slug>/v<N>/`: a `task.json` plus the files it references with `{ "$file": "<path>" }`, embedded in `HireLab.Tasks` and imported into the database as a system task. Always published (ADR 0030). In code: `SeedTaskPackage`, `SeedPackageReader`. |
| **Seed import** | The migration worker step that imports the seed packages as system tasks, idempotently by slug and version number. A bad package or an edited imported version stops the worker. Switched by `TaskBank:ImportSeedTasks` (on by default). In code: `SeedTaskImport`. |
| **Tasks lock** | `src/Tasks/tasks.lock.json`: a hash of the files of every published seed package. A CI test fails when a locked version changes or disappears, or a new one isn't locked; `eng/update-tasks-lock.ps1` adds new versions (ADR 0030). |
| **Duplicate** | A team's draft copy of another task. It remembers its source, which is then hidden from the team's bank. |
| **Hidden task** | A Global task a team's manager has hidden from that team's bank. Reachable through "Show hidden". |
| **Task type** | The kind of task and the code that comes with it: content and response models, a candidate UI, a review UI and an editor. Code review, AI assistant, live coding. |
| **Open question** | The simplest task type (`open-question`): the candidate reads a Markdown prompt and writes a Markdown answer of at most 20,000 characters, with a preview. It has no staff content and suggests no scores; the reference answer, interviewer notes and rubric carry the judgement. In code: `OpenQuestionTaskType`. |
| **Task type key** | A task type's stable kebab-case name, such as `code-review`. Tasks, seed packages, candidate routes (`/api/candidate/tasks/<key>`) and the frontend registries use it; it is never renamed (ADR 0028). In code: `ITaskType.Key`. |
| **Task type registry** | The task types the host knows, by key. In the backend it fails startup on a duplicate key; in the frontend there is one per entry point (`candidate`, `review`, `editor`) mapping the key to a lazily loaded component. In code: `ITaskTypeRegistry`, `TaskTypeRegistry`. |
| **Task type catalog** | The one list of task types HireLab ships, registered by the API, the migration worker and the tasks lock guard. In code: `TaskTypeCatalog.AddTaskTypes()` in `HireLab.TaskTypes.Catalog`. |
| **Candidate content / Staff content** | The two parts of a task version's content. The candidate part is what the candidate's UI renders; the staff part (planted secrets, expected findings …) never reaches the candidate API. Stored in two columns. In code: `TaskContent`, `candidate_content`, `staff_content`. |
| **Content schema version** | The version of a task type's content models, stored with every task version. A mismatch with the registered type fails loudly. In code: `ITaskType.ContentSchemaVersion`; responses have a `ResponseSchemaVersion`. |
| **Criterion suggestion** | A task type's proposed value for one rubric criterion, with a reason, which the interviewer confirms or overrides. In code: `CriterionSuggestion`. |
| **Task bank** | The catalogue of the tasks a manager or interviewer can see (their team's and every Global one, system tasks included), each shown by its active version. Filterable by tags (all of them), level, task type and text in the title or summary. Archived tasks and tasks whose task type is no longer registered are left out. |
| **Bank visibility** | The badge the task bank shows on a task: `Team` (a team task only its team sees), `Global` (a team task every team sees) or `System` (a system task). In code: `BankVisibility`. |
| **Candidate preview** | The task's `candidate` component rendered for staff with a throwaway response that is never saved. A task type without a registered component shows "No preview". In code: `TaskPreview` (`hl-task-preview`). |
| **Level** | A task's difficulty: `Junior`, `Mid` or `Senior`. |
| **Tag** | A free label on a task, such as `csharp`, `cqrs`, `security` or `role:qa`. |
| **Reference answer** | Markdown describing what a strong answer contains. It is shown next to the candidate's response, never to the candidate. |
| **Interviewer notes** | Markdown on a task or a job position with hints for a stuck candidate and follow-up questions. Staff only. |
| **Rubric** | The scoring criteria of a task, defined with the task. |
| **Criterion** | One rubric item. A `scale` criterion is scored 0–4 and weighted; a `check` criterion is Yes / No with an expected answer. Any criterion can be "not assessed". |
| **Critical check** | A `check` criterion whose failure is highlighted above the score. |
| **Interview session** | One meeting with a candidate, planned from their profile by any manager or interviewer of the team, who all control it. It has an optional schedule, a task queue and a state: `Planned` → `Live` → `Finished`. Only a planned session can be deleted; a finished one can't be reopened. Refused for an anonymised candidate or a closed position (ADR 0031). In code: `InterviewSession`. |
| **Session N** | How a session is shown: N is its number among its candidate's sessions (1, 2, 3 …). Sessions have no title. In code: `InterviewSession.Number`. |
| **Sessions page** | The team's `Planned` and `Live` sessions, soonest first: Live ones, then by schedule, unscheduled ones last. |
| **Task queue** | The ordered tasks of a session, at most 30, each task at most once. Tasks are added from the task bank, removed or reordered while the session is Planned, and those that haven't started also while it is Live. Every change raises the session's queue revision. |
| **Session task** | One task in a queue. When queued, it pins the task's active version and stores a task version snapshot. Its state is `Pending`, `Current` or `Done`. In code: `SessionTask`. |
| **Not reached** | A `Pending` session task of a `Finished` session: the session ended before the candidate got to it. It keeps its pin and is shown as "not reached". |
| **Go Live** | Starting a `Planned` session: its first task becomes `Current`. Refused with an empty queue, for an anonymised candidate or a closed position. |
| **Mark done** | The interviewer completing the `Current` task: it becomes `Done` and the next `Pending` task `Current`. After the last task the session stays `Live` until it is finished. |
| **Re-pin** | A `Pending` session task following its task's active version: when the queue is opened or the task becomes `Current`, a changed active version is pinned with a fresh snapshot. An archived task, or one whose task type is no longer registered, keeps its pin (ADR 0028, ADR 0031). In code: `LazyRepinning`. |
| **Candidate link** | An unguessable URL (`/s/{token}`) that gives the candidate access to one session. Before Live it shows a waiting page; after Finished it stops working. Only its hash is stored, so it is shown once, when it is created; to send it again, the interviewer regenerates it, which revokes the old link and the cookies issued from it (ADR 0031). In code: `CandidateLink`. |
| **Regenerate link** | Replacing a session's candidate link with a new one, while the session is Planned or Live. The old link and every candidate cookie exchanged for it stop working. Refused for an anonymised candidate or a closed position. |
| **Link exchange** | Opening a candidate link: the candidate app sends the token to the API, which answers with the candidate cookie. The cookie carries the session and link ids, is checked on every request and lasts at most 12 hours (ADR 0008). |
| **Waiting page** | What the candidate sees while their session is Planned. It moves on to the first task by itself when the session goes Live. In code: `InterviewStage.Waiting`. |
| **Closing screen** | What the candidate sees once every task of a Live session is Done, until the interviewer finishes the session. In code: `InterviewStage.Closing`. |
| **Candidate scope** | Code that reads a candidate's own session for the candidate link or cookie, by the token's hash or the cookie's ids instead of a team. The only request code allowed to bypass the team query filter (ADR 0031). In code: `ICandidateScope`. |
| **Response** | Everything a candidate produced for a session task: comments, files, prompts. It is saved continuously. |
| **Evaluation** | One interviewer's rubric scores and notes for a candidate's session. Its author and the manager can see it. |
| **Decision** | The manager's final hire / no-hire for a candidate, with a summary. |
| **Admin / Manager / Interviewer** | User roles. See `docs/vision.md#roles`. There is exactly one admin, who has no team. |
| **User** | A staff account: email (the login), display name, role, team and an active flag. Candidates are not users. |
| **Team** | An entity with its own id and name that owns job positions, sessions and evaluations. It has at most one active manager and any number of interviewers, and keeps its data when its manager changes. |
| **Team-owned** | Data that belongs to one team (job positions, sessions, evaluations …). Only that team's manager and interviewers see it; the admin sees none. In code: `ITeamOwned`. |
| **System job** | Work that runs outside any user's request, on behalf of no team, such as the migration worker and the orphan sweep. Only system jobs may read across teams by bypassing the team query filter (ADR 0009); a candidate scope bypasses it only for the candidate's own session. In code: hosted services and `ISystemJob`. |
| **Orphan sweep** | The hourly system job in the API that deletes attachment blobs without an attachment row (orphans) once they are older than the grace period (an hour by default), so an upload still in progress keeps its blob. Blobs whose name it doesn't recognise are kept (ADR 0027). In code: `OrphanAttachmentSweep`. |
| **Deactivation** | Switching a user off instead of deleting them: they can't log in and their sessions end within 5 minutes. The admin deactivates anyone but themselves; a manager deactivates their own interviewers. It also revokes the pending invite and reset links the user issued and the reset links for them, so a departing manager's links neither create accounts nor take any over. Reversible by reactivation, which is refused for a manager while their team has another active manager. |
| **Handover** | Giving a team a new manager: the admin deactivates the old manager, the team shows "No manager", and the admin invites a new manager into the same team. |
| **Reassignment** | The admin moving an interviewer to another team. Their sessions end within 5 minutes, after which they see only the new team's data. Their pending reset links are revoked; invites are not affected. Managers are not reassigned; a team changes manager by handover. |
| **Security stamp** | A random value on each user that changes on deactivation, role or team change and password reset. Sessions issued before the change end at the next check, at most 5 minutes later. |
| **Invite link** | A one-time link, valid for 72 hours, that creates a user account in a given role and team. The admin invites a manager into a new team (created only when the link is redeemed) or into an existing team without an active manager; a manager invites interviewers into their own team. Issuing a new invite for the same email revokes the old one, but only if the issuer manages it: a pending invite from someone else (the admin, or another team's manager) blocks the new one until it is revoked or expires. In code: `Invite`. |
| **Bootstrap invite** | The admin invite link (valid for 24 hours) that the migration job issues while no admin exists, and writes to its log. A manual run with `--issue-admin-link` replaces it, or issues a reset link for the admin once they exist. It never creates a second admin. |
| **Invite state** | The state of an invite or reset link: `Pending` (can be redeemed), `Used`, `Revoked` or `Expired`. Only a pending link works. In code: `OneTimeLinkState`. |
| **Redemption** | Opening an invite link and setting a password: the account is created and the invitee is logged in. |
| **Reset link** | A one-time link, valid for 24 hours, that lets an existing user set a new password. The admin generates it for a manager, a manager for their own interviewers, and it is sent by hand. Redeeming it clears the lockout and ends the user's existing sessions; the user then logs in with the new password. Generating a new link revokes the user's previous unused one; deactivating or reassigning the user, or deactivating the issuer, revokes it too. In code: `ResetLink`. |
